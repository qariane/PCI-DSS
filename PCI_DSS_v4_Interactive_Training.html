01 — Foundations

What PCI DSS actually is

The Payment Card Industry Data Security Standard (PCI DSS) is a set of technical and operational security requirements created by the major card brands (Visa, Mastercard, Amex, Discover, JCB) through the PCI Security Standards Council. If your organisation stores, processes, or transmits card data — in any amount — PCI DSS applies to you.

Who has to comply?

Any merchant or service provider that touches cardholder data (CHD) or sensitive authentication data (SAD) — from a single-location retailer to a global e-commerce platform. The depth of validation required (a Self-Assessment Questionnaire vs. a full Report on Compliance by a QSA) scales with transaction volume and risk.

Why it exists

Card data is a direct, liquid target for criminals — a stolen number can be monetised in minutes. PCI DSS exists because card brands need every party that touches that data to hold the line at a common standard, or the entire payment ecosystem's trust breaks down.

The four compliance statuses used in your assessment

In Place

The control is fully implemented, documented, and operating as intended. Evidence has been reviewed to confirm it.

In Place with CCW

The literal requirement isn't met, but a documented Compensating Control Worksheet shows an alternative control addresses the same risk.

Not in Place

The control has not been implemented. This is a compliance gap and a real security exposure that needs remediation.

Not Applicable

The requirement genuinely doesn't apply to this environment (e.g., no wireless in scope) — but this must be justified, not assumed.

Two kinds of sensitive data

Cardholder Data (CHD)

The primary account number (PAN), and when stored alongside it: cardholder name, expiry date, service code. CHD may be stored, but only if protected — masked, encrypted, and minimised.

Sensitive Authentication Data (SAD)

Full magnetic-stripe/chip data, the CVV/CVC security code, and PINs. SAD must never be stored after a transaction is authorised — not even in encrypted form.

03 — Methodology

How risk is scored in your assessment

Every "Not in Place" (and every control generally) is scored using a simple, standard risk formula: Risk Level = Likelihood × Impact. Try it yourself:

1
Risk Level
LOW
1–10 = Low
11–50 = Medium
51–100 = High / Critical

In your assessment, every "Not in Place" control still carries this score — it represents the risk your organisation is currently exposed to because the control is missing, not a score against a passing test.

Network Security Controls – Processes & Mechanisms
IN PLACE
RISK 25
▸
“Are processes and mechanisms for implementing and maintaining network security controls documented, kept current, and known to all affected parties?”
Why this control matters

A written, current policy tells IT and security teams exactly how firewalls and routers must be configured and maintained, so protection doesn't depend on one person's memory.

Risk if not in place

Without documented rules, configurations drift silently between admins, mistakes go unnoticed, and there is no baseline to audit against — the network perimeter erodes over time without anyone realizing it.

“Are network security controls (NSCs) configured to filter traffic between trusted and untrusted networks? Do rule sets prevent all inbound and outbound traffic not expressly permitted?”
Why this control matters

06 — Check Your Understanding

Knowledge check

Five quick questions. Pick an answer to see instant feedback.

SCORE0 / 5
1. Sensitive Authentication Data (SAD), like a card's CVV, may be stored after the transaction is authorised as long as it's encrypted.
False. SAD must never be stored post-authorisation, encrypted or not — it's exactly the data needed to commit fraud, so PCI DSS prohibits retaining it at all.
2. What does 'Risk Level' represent in this assessment?
Risk Level = Likelihood × Impact. It quantifies exposure, not effort or cost — a High likelihood, High impact gap scores up to 100.
3. Which control most directly reduces the damage a single stolen password can cause?
MFA (Req 8.4) means a password alone isn't enough to get in — it's the single most effective control against credential-based attacks.
4. Why does PCI DSS require masking the PAN (showing only first 6 / last 4 digits) even for authorised staff?
Masking limits exposure of the full number even to authorised staff — reducing the chance of casual copying, photographing, or misuse, intentional or not.
5. An organisation has good firewalls (Req 1–2) but no logging or monitoring (Req 10) in place. What's the main risk?
No control blocks 100% of attacks. Without logging and monitoring, a breach can go undetected for months, with no evidence trail to understand what happened.
07 — Reference

Glossary

Every acronym and term used throughout this training and the source assessment, in one place.

CDE
Cardholder Data Environment

The people, processes, and technology that store, process, or transmit cardholder data or sensitive authentication data, plus anything connected to or that could impact the security of that data.

CHD
Cardholder Data

At minimum, the full primary account number (PAN). May also include cardholder name, expiration date, or service code when stored with the PAN.

SAD
Sensitive Authentication Data

Security-related data used to authenticate a card transaction — full track/chip data, card verification codes (CVV/CVC), and PINs. Must never be stored after authorisation.

PAN
Primary Account Number

The unique payment card number (typically 14–19 digits) that identifies the issuer and the cardholder account. The core piece of data PCI DSS protects.

PCI DSS
Payment Card Industry Data Security Standard

A set of 12 security requirements, maintained by the PCI Security Standards Council, that any organisation storing, processing, or transmitting card data must meet.

PCI SSC
PCI Security Standards Council

The industry body — founded by Visa, Mastercard, American Express, Discover, and JCB — that develops and maintains PCI DSS and related standards.

QSA
Qualified Security Assessor

An individual certified by the PCI SSC to formally assess an organisation's compliance with PCI DSS, typically producing a Report on Compliance (ROC).

ASV
Approved Scanning Vendor

A company certified by the PCI SSC to perform the external vulnerability scans PCI DSS requires at least quarterly.

SAQ
Self-Assessment Questionnaire

A validation tool used by eligible merchants to self-report PCI DSS compliance rather than undergo a full external QSA assessment. Different types (A, A-EP, B, C, D, etc.) apply based on how the organisation handles card data.

ROC
Report on Compliance

The detailed report a QSA produces after formally assessing an organisation against all applicable PCI DSS requirements — typically required for larger merchants and all service providers.

TLS
Transport Layer Security

The cryptographic protocol that encrypts data travelling over a network (the successor to SSL). PCI DSS requires TLS 1.2 or higher to protect card data in transit.

HSM
Hardware Security Module

A dedicated, tamper-resistant physical device used to generate, store, and manage cryptographic keys, keeping them isolated from the systems that use them.

MFA
Multi-Factor Authentication

Authentication requiring two or more independent factors (something you know, have, or are) before granting access — dramatically reducing the risk of a stolen password alone leading to a breach.

NSC
Network Security Controls

Technologies (firewalls, cloud security groups, routers with ACLs, etc.) that enforce network traffic policies between segments of differing trust levels.

WAF
Web Application Firewall

A security control that filters, monitors, and blocks malicious HTTP traffic to and from a web application, defending against attacks like SQL injection and cross-site scripting.

FIM
File Integrity Monitoring

A change-detection technology that alerts when critical system or configuration files are modified without authorisation — often an early sign of compromise.

TPSP
Third-Party Service Provider

An external organisation (payment processor, hosting provider, cloud vendor, etc.) that stores, processes, or transmits card data on behalf of another entity, or could affect the security of that data.

Tokenisation
Tokenisation

Replacing a PAN with a non-sensitive substitute value (a token) that has no exploitable value outside the specific system that issued it, reducing the scope of systems that handle real card data.

Network Segmentation
Network Segmentation

Isolating the CDE from the rest of an organisation's network so that only necessary, controlled traffic can reach systems that handle card data — shrinking the PCI DSS assessment scope and the attack surface.

Least Privilege
Least Privilege

The principle that a user or system account should have only the minimum access necessary to perform its job — nothing more.

SAST / DAST
Static / Dynamic Application Security Testing

Automated techniques for finding vulnerabilities in software: SAST analyses source code without running it; DAST tests a running application from the outside, the way an attacker would.

OWASP
Open Worldwide Application Security Project

A nonprofit community that publishes widely-used, freely available resources on web application security, including the well-known OWASP Top 10 list of common vulnerabilities.

E-Skimming / Magecart
E-Skimming / Magecart

A category of attack where malicious code is injected into a website's checkout page to silently capture payment details as customers type them in.

IDS / IPS
Intrusion Detection / Prevention System

Technology that monitors network or system activity for malicious behaviour (IDS) and can automatically block it (IPS).

NTP
Network Time Protocol

The standard protocol used to synchronise clocks across computer systems, ensuring timestamps in logs from different systems can be reliably compared.

Compensating Control
Compensating Control

An alternative control used when an organisation cannot meet a PCI DSS requirement exactly as stated, but implements another control that sufficiently addresses the same risk — documented in a Compensating Control Worksheet (CCW).

Encryption at Rest / in Transit
Encryption at Rest / in Transit

'At rest' means data is encrypted while stored (on disk, in a database); 'in transit' means it's encrypted while moving across a network. PCI DSS requires both for cardholder data.

Vulnerability Scan vs. Penetration Test
Vulnerability Scan vs. Penetration Test

A vulnerability scan is an automated check for known weaknesses; a penetration test is a hands-on, human-led attempt to actively exploit weaknesses, including ones automated tools would miss.

Change Control
Change Control

A formal process for reviewing, approving, testing, and documenting changes to systems before they go live, to prevent uncontrolled changes from introducing new risk.

Data Retention Policy
Data Retention Policy

A documented rule for how long data may be kept before it must be securely deleted — for cardholder data, PCI DSS requires keeping only what's needed, for as long as it's needed.

Merchant Level
Merchant Level

A classification (Level 1–4) based primarily on annual transaction volume that determines the depth of PCI DSS validation a merchant must undergo (e.g., full QSA assessment vs. a self-assessment questionnaire).
