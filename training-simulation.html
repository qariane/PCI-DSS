API Security

How we make sure only trusted, authorised systems can communicate with Mastercard — and how we detect the ones that shouldn't be.

The Problem We're Solving

Why API security is not optional

APIs are the front door to Mastercard's payment systems. Without proper controls, that door is open to anyone who can find it.

🚪

No Identity Check

Without mTLS, any system on the internet can send requests pretending to be a legitimate partner. We cannot tell the difference.

🔓

Over-permissioned Access

Without OAuth scopes, a system that should only read transaction status could also trigger payments. Least privilege is not enforced.

💥

No Abuse Prevention

Without rate limiting, a single compromised client can flood our APIs with millions of card enumeration requests. We wouldn't know until the damage was done.

💡
The Real Risk

In 2019, a major US retailer lost 100 million customer records because their API had no authentication on an internal endpoint. The attacker simply knew the URL. No password. No certificate. Nothing.

Control 1 of 4

Mutual TLS (mTLS) — The Two-Way ID Check

In standard HTTPS, only the server proves who it is. In mTLS, both sides present a certificate before a single byte of data is exchanged.

Two Government Agents

Two agents from different agencies meet to share intelligence. Neither talks until both have seen the other's badge, checked it's not expired, and confirmed it hasn't been revoked. Only then do they share anything.

  • Blocks impersonation — a fake system cannot forge a valid certificate
  • Certificate rotation every 90 days — limits damage if one is compromised

OAuth 2.0 — Permission, Not Just Identity

mTLS proves who a system is. OAuth 2.0 proves what that system is allowed to do — with short-lived tokens that expire before they can be reused.

Control 3 of 4

Rate Limiting & Anomaly Detection

Rate limiting caps volume. Anomaly detection catches attackers smart enough to stay under the cap but suspicious enough to trigger an alert.

💡
The ATM Analogy

A bank limits PIN attempts to 3 per card — that's rate limiting. Anomaly detection is the security system noticing someone is trying a different card at every ATM in the building, one attempt per machine. Each machine sees nothing unusual. The security system sees everything.

  • Rate limiting: 100 requests/min per client. Burst allows 200 for brief spikes. Sustained abuse is blocked.
  • HTTP 429: The standard "Too Many Requests" response. The client must back off and retry.
  • Anomaly detection: Baseline of normal traffic established. Anything more than 20% above baseline triggers a SIEM alert.
  • Automated response: Alert → investigate → throttle or block session automatically.

What Anomaly Detection Watches For
  • Traffic spikes above the 20% baseline threshold
  • Rapid sequential card number queries (enumeration)
  • Requests from unusual geographic locations
  • Multiple failed authentication attempts in a short window
  • Patterns consistent with automated bot activity
Control 4 of 4

Monitoring & Logging — If It Isn't Logged, It Didn't Happen

Every API request, success or failure, is logged to our SIEM. Without this, we cannot investigate incidents or prove compliance during an audit.

What We Log on Every API Call
  • Timestamp, source IP, destination endpoint
  • Authentication result (success / failure + reason)
  • HTTP method, status code, response time
  • OAuth token claims (issuer, audience, scope)
  • Certificate identity (for mTLS connections)
  • Rate limit status and any throttle events
💡
Why Logs Matter

When a breach is discovered, the first question is always "how long has this been going on?" Without logs, you cannot answer that. With 90 days of logs in SIEM, you can trace exactly when an attacker first appeared, what they accessed, and what they tried.

Tokenization

How we make sure the real card number disappears from our systems the moment it is captured — and never appears again.

PANTokensHSMToken VaultAES-256FIPS 140-2
The Asset We're Protecting

What is a PAN and why is it so valuable?

The Primary Account Number is the most sensitive element in a payment transaction. Every system that sees it becomes a target — and a compliance scope item.

PAN — Primary Account Number
4532 •••• •••• 1234

The 16-digit card number. If an attacker obtains this, they can make fraudulent transactions immediately. It is the single most valuable piece of data in our environment.

💡
The Scope Problem

Imagine the PAN travels through 20 systems before the transaction settles. That means 20 systems are now in scope for PCI DSS — each one needs to be audited, tested, and secured. Tokenization reduces that number to 1.

Risk Without Tokenization
Risk 1
Database breachPAN stored in a database → one breach exposes all customers
Risk 2
Log injectionPAN accidentally appears in application logs → any log access = PAN access
Risk 3
Insider threatDeveloper with database access can query PAN for any customer
Risk 4
Wide compliance scopeEvery system that touches PAN must be PCI DSS audited
The Core Mechanism

How Tokenization Works — Step by Step

The PAN is captured once, replaced immediately, and never seen again by any business system.

①
Customer enters PAN at payment terminal
②
PAN is encrypted in transit using TLS 1.2+ — nobody can intercept it
③
Tokenization service receives the PAN — this is the last system that ever sees it
④
A random, unique token is generated — no mathematical link to the PAN
⑤
PAN is encrypted with AES-256 and stored in the HSM-protected vault. PAN leaves this vault for nothing.
⑥
Token is returned to the application. All downstream systems, databases, and logs use only the token.
💡
The Cloakroom Ticket

You hand in your coat (PAN) at the cloakroom. You get a numbered ticket (token). You use the ticket number for everything — telling friends, paying, proving ownership. The coat stays locked in the back. If someone steals your ticket, they just have a number. They cannot get the coat without matching ID.

Token Design

Irreversible Tokens — Why "Random" Is Not Enough

Token generation must be non-deterministic. If there is any pattern or formula linking a token to its PAN, a determined attacker can reverse-engineer it.

❌ Weak Token Design (Deterministic)

A formula converts PAN → Token. Given enough PAN-token pairs, an attacker can discover the formula and reverse every token in the database back to real PANs.

✓ Strong Token Design (Non-Deterministic)

The same PAN tokenized twice produces two completely different, unrelated tokens. There is no formula. You cannot work backwards. The only way to find the PAN is to query the vault — which requires breaking through all the access controls.

💡
The Lottery Ticket

Replace your passport number with a random lottery number. There is no conversion formula. Even if someone collects a million lottery numbers, they cannot find a single real passport. That is what non-deterministic means.

The Protected Storage

The HSM-Protected Token Vault

The vault stores the PAN-to-token mapping. A Hardware Security Module protects the encryption keys — ensuring they can never be extracted, even by someone with server access.

💡
The Bank Vault Analogy

The vault room holds the contents (PAN mappings). The HSM is the combination — stored inside a physical safe that's bolted to the floor. The safe performs the unlocking operation internally. The combination never leaves. You cannot extract it with software, you cannot copy it. The only way in is through the safe's own mechanism.

  • FIPS 140-2/3 compliant — US government standard for cryptographic hardware
  • AES-256 encryption — industry standard for data at rest
  • Keys never leave HSM — all encryption/decryption happens inside the device
  • Key rotation enforced — regular rotation limits exposure if keys are ever compromised
  • RBAC + MFA — role-based access with multi-factor authentication required

Zone Architecture

The Network Is Divided into Six Zones

Each zone has a different trust level. Traffic between zones must pass through a firewall. You cannot skip zones — every hop is controlled and logged.

Internet / PublicExternal users and clients. No direct access to any internal system.UNTRUSTED
DMZ — API GatewayEntry point for API traffic. WAF, rate limiting, TLS/mTLS enforced here.SEMI-TRUSTED
Application ZoneBackend services. Can only reach the CDE for tokenization requests. No direct internet access.INTERNAL
CDE — Cardholder Data EnvironmentTokenization service and token vault. The most restricted zone. Strict isolation enforced at all times.MOST RESTRICTED
Admin ZoneAdministrative users only. All access to CDE goes through bastion host. MFA required.CONTROLLED
Logging / SIEM ZoneReceives logs from CDE and all other zones. No return traffic to CDE allowed.RECEIVE-ONLY
💡
The Hospital Analogy

A hospital has a lobby, general wards, and an ICU. You can walk into the lobby freely. The wards need a visitor badge. The ICU needs a badge, a code, a stated reason, and a staff escort. You cannot walk from the lobby to the ICU — you pass through every checkpoint. Our network works the same way.

The Core Principle

Default Deny — The Most Important Rule

The entire firewall model is built on one principle: everything is blocked unless there is an explicit rule saying otherwise.

❌ Default Allow (What We Don't Do)

Traffic flows freely unless a rule blocks it. An attacker who finds a gap in the rules can reach any system. New systems added to the network are immediately accessible.

✓ Default Deny (Our Model)

All traffic is blocked. To open a path, you write an explicit, reviewed, documented rule. New systems are completely isolated until access is deliberately granted.

💡
The Guest List

Our firewall is like a nightclub with a guest list. Everyone is outside by default. You only get in if your name is on the list. We decide who's on the list — the list is FW-001 to FW-007. FW-008 and FW-010 say: if you're not on the list, you don't get in. No exceptions.

The Two Foundation Rules
FW-008
Any → CDE — DENY ALLThe CDE is completely sealed. Only FW-003 and FW-004 (explicit allows) can breach this. Everything else is refused.
FW-010
Any → Any — DENY ALLThe catch-all. Any traffic not matched by a rule above this is blocked. No gaps. No accidents. No undefined paths.

Week 3 Complete

What We've Built — How It All Connects

Three control layers. Three deliverables. One integrated defence against payment data compromise.

🔐
Layer 1 — API Security

mTLS + OAuth + Rate Limiting

Only verified, authorised, well-behaved systems can reach our APIs. Everything else is rejected before it touches data.

💳
Layer 2 — Tokenization

Real-time PAN → Token

Even if an attacker gets through the API layer, they find only useless tokens everywhere — no real PANs to steal.

🌐
Layer 3 — Network

Default Deny + CDE Isolation

Even if an attacker reaches the network, the CDE is sealed. No path to the vault exists except the ones we deliberately opened.

💡
The Defence in Depth Payoff

Each layer assumes the layer before it will sometimes fail. API security fails → tokenization means there's nothing useful to steal. Tokenization is breached → network segmentation means the attacker cannot reach the vault. The vault is targeted → HSM keys cannot be extracted. That's what defence in depth actually means in practice.
