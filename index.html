🔐 What is mTLS and why does it matter?

Mutual TLS (mTLS) is like a two-way ID check at a secure door. In regular TLS (HTTPS), only the server proves who it is. In mTLS, both the client and the server must show a certificate before any data is exchanged.

💡
Real-World Analogy

Imagine two government agents meeting. They don't just show ID once — each one checks the other's badge before talking. If either can't produce valid credentials, the conversation never happens.

TLS Version
1.2+ (prefer 1.3)
Older versions have known vulnerabilities
Cert Rotation
Every 90 days
Limits window if a cert is compromised
Revocation
CRL / OCSP
Instantly block stolen certificates
Prevents
MITM Attacks
Nobody can silently intercept traffic

Without mTLS, a malicious system could impersonate a legitimate service and intercept or inject payment data. With mTLS, every connection is cryptographically verified before a single byte is transferred.

🔑 OAuth 2.0 — Who is allowed to do what?

OAuth 2.0 handles authorization — not just "is this system allowed in?" (that's mTLS), but "what is this system allowed to do?" It uses short-lived tokens instead of passwords, so even if a token is captured, it expires quickly.

💡
Real-World Analogy

Think of OAuth tokens like a valet parking ticket. The valet (API client) gets a limited-time slip that only allows parking — not access to your trunk or glove box. When the time is up, the slip is worthless.

Token Type
JWT
JSON Web Token — signed and verifiable
Access Token
15 minutes
Short life = small attack window
Refresh Token
24 hours
Get a new access token without re-login
Access Model
Least Privilege
Each token only covers what's needed

Every JWT token must be validated on arrival: check the issuer (who made it), the audience (who it's for), and the expiry (is it still valid?). If any check fails, the request is rejected immediately.

🚦 Rate Limiting & Anomaly Detection

Rate limiting caps how many requests any single client can make in a time window. Anomaly detection watches the pattern of those requests to spot attacks that stay under the limit but behave suspiciously.

💡
Real-World Analogy

A bank only lets you attempt your PIN 3 times. Rate limiting is that rule. Anomaly detection is the teller noticing that someone is trying cards at every ATM in the building — even if each one is under the 3-attempt limit.

Standard Limit
100 req / min
Per client per API key
Burst Limit
200 req / min
Short peaks allowed, sustained abuse blocked
HTTP Response
429 Too Many
Standard response when limit exceeded
Alert Threshold
> 20% spike
Triggers SIEM alert for investigation

Anomaly detection integrates with your SIEM to establish a baseline of "normal" traffic. When requests spike, originate from unusual locations, or show abnormal patterns like rapid sequential card queries, an automated alert fires and the session can be blocked or throttled.

MODULE 02 · TOKENIZATION
Replacing PAN with Safe Tokens
How sensitive card numbers disappear from your systems entirely

💳 What is a PAN and why is it dangerous?

The Primary Account Number (PAN) is the 16-digit number on a payment card. It is the most sensitive piece of data in a payment system — if stolen, it can be used to make fraudulent transactions directly.

💡
The Core Problem

Every system that sees, stores, or passes the real PAN becomes a target. If 20 systems touch the PAN during a transaction, all 20 are in scope for PCI DSS and need to be secured. Tokenization reduces this to one.

Tokenization replaces the PAN with a random, meaningless token the instant it is captured. The real PAN goes into a locked vault. From that point forward, every system uses only the token — which is useless to an attacker even if stolen.

→
Token generated
→
PAN stored in vault
→
Token used everywhere else

🔒 Irreversible Tokens — Why "random" matters

Not all tokens are equal. A weak token might be generated using a predictable formula — which means an attacker who captures enough tokens could reverse-engineer the original PAN. Irreversible tokens use non-deterministic (truly random) generation with no mathematical link to the PAN.

💡
Real-World Analogy

Imagine replacing your passport number with a random lottery number. There is no formula that converts one to the other. Even if someone steals all the lottery numbers, they cannot work backwards to find anyone's passport. That is what irreversibility means.

Non-sensitive

Legacy only
Format-preserving tokens only for legacy system compatibility

🏦 HSM-Protected Token Vaults

The token vault stores the mapping between PAN and token. It is the most sensitive system in the payment environment. A Hardware Security Module (HSM) is a dedicated physical device that handles all encryption operations and stores the keys — ensuring keys never exist in software where they could be extracted.

💡
Real-World Analogy

A bank vault has both a physical safe (the HSM — holds the combination) and the vault room (the token vault — holds the actual contents). You cannot open the vault without the safe's combination, and the combination never leaves the physical safe.

🌐 Network Zones — Who lives where?

The network is divided into zones. Each zone has a different trust level. Traffic between zones must pass through a firewall that enforces strict rules. The most sensitive zone — where PAN data lives — is the Cardholder Data Environment (CDE).

Internet / Public
Untrusted
External users and clients. No direct access to anything.
DMZ (API Gateway)
Semi-trusted
Entry point. Has WAF, rate limiting, TLS enforcement.
Application Zone
Internal
Backend services. Can only talk to CDE for tokenization.
CDE
Most Restricted

Admin Zone
Controlled
Admin users. Access via bastion host only. MFA required.
SIEM / Logging
Receive-only
CDE pushes logs here. No return traffic allowed.
💡
Real-World Analogy

Think of a hospital. The lobby (Internet) is open to all. The wards (Application Zone) require a badge. The ICU (CDE) requires a badge, a code, and a reason to be there. You cannot walk from the lobby directly to the ICU — you must pass through every checkpoint.

🔥 Firewall Rules — Default Deny Model

The entire firewall model is built on one principle: everything is blocked unless explicitly allowed. Rules FW-008 and FW-010 are the backbone — all other rules are controlled exceptions to the default deny.

Key Principle

Rules are read top-to-bottom. FW-003 says "App Zone to CDE on 443 is allowed." FW-008 says "everything else to CDE is denied." The specific rule wins — but only because it is listed before the default deny. Order matters.

🛡️ Admin Access — The Bastion Host Model

Administrators need to manage CDE systems, but direct access from the corporate network to the CDE would break segmentation. The solution: a bastion host (jump server) — a single, hardened entry point that all admin traffic must pass through.
